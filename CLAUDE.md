# Falcon BMS Companion: notes for AI-assisted maintenance

Three deliverables live in this repo, all built from the same Kotlin/Compose screens in `app/src/main/java`:
1. **Android app** `app/`: Kotlin + Jetpack Compose + Material 3, package `com.bmscompanion.app`, a single APK (charts and every map style/zoom level included).
2. **BMS Companion for Windows** `desktop/`: Compose for Desktop. It reads Falcon BMS (the former C# bridge, ported to Kotlin in `desktop/.../bridge/`), serves the API, the browser version and the bundled data on one port (47474), and is the full app. One window: the light **server page** or the **full app**. Packaged as MSI + portable zip with its own Java runtime.
3. **Browser version** `web/`: Kotlin/Wasm + Compose for Web. The same app running in the browser (iPhone, iPad, any browser); served by the PC program from its resources (`/webapp`).

## Ground rules
- **The BMS install is read-only except where a feature must write, and then only safely.** The writers, and the rules each follows:
  - **Config** (`User/Config/*.cfg`) and **Weather** (`Data/<theater>/Campaign/*.fmap` and `WeatherMapsUpdates/`) follow the **backup rule**, each with its own restore button: off until switched on; a one-time copy of every original **into the BMS folder beside the files** (`BackUp/`, `Campaign/BMS Companion Backup/`), never into `%APPDATA%`, so it survives an app update, a reinstall or a new PC; a plain-English README beside the copies saying how to restore **by hand without this program**; every write derived from the original, so edits never compound; never written in place (temp file, then an atomic move); and nothing may throw — the reason comes back for the page to show.
  - **Everything the Planner writes is written the way WDP writes it: directly, with no backup** (the user's decision) — no question first, nothing to switch on, no copy, README or record — but still through a temp file and an atomic move, and still never throwing (the reason comes back as a sentence). The **cockpit kneeboard pages** (`<3ddatadir>/KoreaObj/7982-7997.dds`, Upd Kneeboard): only the pages chosen, each kept in its own format, and a page file that does not exist is never created. The **pilot's data cartridge** (`User/Config/<callsign>.ini`, Save to DTC): only the edited keys, applied to the file as it is on disk, so edits never compound (a `BMS Companion Backup/` folder a 1.3.8 test build left in `User/Config` is left alone and never read). **Campaign and TE saves and their companion files**: today only a TE's own `<name>.ini` (the pilot's TEs and trainings and BMS's `TE_BMS_*`/`TR_BMS_*` alike), whose `[STPT]` keys Save to DTC writes with that TE open, when the save's own `SaveFile` agrees with its name; the Planner never writes a `.cam`/`.tac`. **The Planner's own folder** (`User/BMS Companion Planner/`, laid out as WDP's program folder: `Files/<part>`, `SavedMaps`, `DataCards` with `PlanPic` — `PcFileRoutes.SKELETON`): what WDP keeps in its own folder and the pilot saves from the Planner's file windows — the DTC page's backups (`.ews`, `.pth` …), personal PPTs (`.ppi`), backup DataCards (`.bdc`), `Codewords.ini`/`PackageTiming.ini`, the saved pictures, and the PC's **cartridge ledger** (`Ledger/<callsign>.json`, written at every Save to DTC); made (with that layout) the first time a file window or the ledger needs it, with the files an earlier 1.3.8 build kept in `Documents/BMS Companion Planner` copied in once (never moved or deleted). The DataCards part can be moved by the pilot anywhere outside the BMS folder and WDP's (inside BMS only within the Planner's folder; `PlannerDataCardDir`, `/api/files/planner`, which refuses the rest in a sentence). Never WDP's own folder, never `User/Config` (only the cartridge goes there).
  - **A switch of the Mission section's mode writes too**, by itself and without asking (`ModeSwitchReset`, 1.3.8), by the Planner's rules above (directly, no backup, temp file and atomic move, never throwing), and silently (no notice on any device): **every** leftover of the Planner's in the cartridge and in the TEs' own `.ini` files — each key the ledger says the Planner wrote that still holds exactly its value, whatever flight it was for, the current flight's too; never a key BMS or the pilot wrote since, except the **delivery data**: every `[NAV OFFSETS]` key that places something goes whoever wrote it, ledger or not (an earlier build or WDP wrote them; BMS's DTC window never edits them), at a switch and at a new mission (then keeping only what the ledger says the Planner saved for the new flight), in the cartridge and the current flight's TE `.ini` (`CartridgeStore.navToClear`, `Leftovers.navClearEdits`; the DTC page drops them too, `DtcWiring.clearDeliveryForMission` from `WdpSession.resetAttack`) — with an Undo route kept from the ledger (`CartridgeLedger.cleared`; only where the file still holds the empty value; no longer offered on screen), and the other mode's cockpit kneeboard halves from an earlier flight, given BMS's shipped page back (`KneeboardPrint.putShippedHalves`; never a page created, format kept, no undo — they are BMS's originals; a theater without originals is left and named).
  - **BMS's campaign starts are never opened or written**, by anything: `CampaignStarts` in `CartridgeStore.kt` (an `.obj` part, no flights, or `Save<n>`, `Te_New*`, `Instant`). Open mission lists them greyed with the reason; every other save opens, as in WDP.
  - **BMS's old debug logs** (`User\Logs` or `g_sLogsDirectory`: `<YYYY-MM-DD_HHMMSS>_xlog.txt` and the same session's `_xlog_*.csv`) are deleted only by the radio log's clean-up (`RadioLog.cleanup`/`cleanupDir`/`plan`, 1.3.8): **off** until the pilot turns it on (Setup, `RadioLogCard`; `RadioLogCleanup`, keep the last N sessions — 5 — or N days); at program start, when a new log starts and on **Delete old logs now** (`/api/radio/cleanup/now`); to the **Recycle Bin** (`AcmiStore.recycle`); never the newest session's, never the log being read, never a file written in the last two minutes, never crash dumps, screenshots or anything else; refused by `DevGuard` in a developer run unless the folder is a copy; never throwing (the reason in `RadioLogCleanup.error`). Reading the log itself is read only (opened shared for a moment, appended bytes only).
  - Everything else in the BMS folder is read-only, including during testing. **A developer check cannot write the real install**: while one runs (`SelfTest` sets `bmsc.devcheck`; `BMSC_DEV_GUARD=1` does it for a dev program started by hand) `DevGuard` refuses every route that writes into a BMS folder — cartridge and TE file, weather, cfg and the RTT switch, EZBoards (the run on PRINT too), media delete, ACMI clear, kneeboard print — with "developer run: writes go to a copy only" unless the folder is plainly a copy (no `Falcon BMS.exe` in it or above it, not the registry's BMS folder). **Dev settings must point at a copy**: run checks with a scratch `APPDATA` whose `bridge-settings.json` sets `BmsDirOverride` to a copy of a BMS folder, never the install. To test EZBoards, copy its folder to a temp dir and strip the `SET KNEEBOARD[...]` lines from the copy's `CONFIG_USER.BAT`.
- **No personal data in the repo** (Windows user names, callsigns, absolute user paths, LAN addresses in screenshots). `local.properties`, `dist/`, `posts/` and `tools/pdftext/` are git-ignored. The sample briefing in `desktop/src/main/resources/bridge` (the briefing parser's fixture) has the names taken out. Screenshots are taken on a real install with the callsign and LAN address out of frame.
- **Phone layouts must stay usable.** Tablet-specific layouts use `isWide()` (≥840dp) / `isMedium()` (≥600dp), `AdaptiveSplit` and `Masonry` from `ui/components/Adaptive.kt`. The PC window and the browser page feed their width into the same checks.
- **Shared app code must also compile for the PC and the browser.** After changing `app/src/main/java`, run `./gradlew :desktop:compileKotlin :web:compileKotlinWasmJs`. Don't add Android-only APIs to shared screens (stand-ins: `desktop/src/main/kotlin/shims/`, `web/src/wasmJsMain/kotlin/shims/`). Prefer `kotlin.*` over JVM APIs; the browser version only has stand-ins for `String.format` (patterns in `web/.../Printf.kt`), `Math`, `System`, `Locale` casing, `SimpleDateFormat`/`Date`, `synchronized` (per package in `web/.../shims/jvmapis/`).
- **JSON contract changes are additive.** The server serializes the app's `app/.../data/mission/MissionModels.kt` classes directly; update the producing code in `desktop/.../bridge/` and `docs/PROTOCOL.md`.

A field's **asphalt is a 3D model, not terrain imagery** — Osan's is one FED object, "RKSO Taxiways" — and **the model format is decoded**, so the chart is drawn from BMS's own triangles: a header, a mesh table, then one vertex array, each mesh a plain triangle list. **`tools/extractor/bml-format.md` is the reference** (layout, the six inspection tools, the five checks); `src/bml.mjs` reads a model and `src/pavement.mjs` turns a field's into outlines. Three things decide correctness. **Nothing sits at a fixed offset** — the file opens with a list that declares its own length, so Osan's mesh table is at 100 and Anshan's at 84, and the header's mesh count is not the number of entries (Anshan says 16, has 14): the table ends where the counts use up the vertex total. **The vertex array is found, not computed**, by looking for a long run of records carrying unit normals; being two records out is what once made Osan's triangles straddle the field. **The triangles must tile** — the sum of their areas within a few per cent of their union (Osan 0.99, Anshan 0.99, Gunsan 1.62 and wrong) — and `pavement.mjs` drops anything over 1.25, so 1,485 of 1,720 fields get exact pavement and the rest fall back to the taxi network drawn at real width. The union is rasterised at 3 ft, traced by `outline.mjs` (edge-chaining, because a boundary *walk* gets stuck wherever a shape narrows to one cell and closes the ring straight across the field) and simplified at 9 ft into rings the app fills even-odd. The **taxiway centre line** is the network itself, dashed in yellow (`drawCentreline`). Look at any change with `BMSC_ONLY_FIELD="Osan AB" node render-debug.mjs korea-kto "Osan AB" out.png` — one field builds in a second. ## Common tasks
- **New BMS version:** follow `docs/UPDATING.md` step by step; `docs/DATA-SOURCES.md` says for every feature which BMS file it comes from, how the reading is verified, and what to look at when one of those files changes.
- **Build & run on a device:** `./gradlew installDebug`. Debug builds accept `adb shell am start -n com.bmscompanion.app/.MainActivity --es route mission` to open a route directly (useful for screenshots).
- **PC version from source:** `./gradlew :desktop:run` (builds the browser version into its resources first; the first web build downloads Node/Yarn/Binaryen and takes minutes). Env: `BMSC_ROUTE=mission` opens a route, `BMSC_PORT=47490` another port (e.g. when another copy uses 47474), `BMSC_SHOW_ADDRESS=192.168.1.20` + `BMSC_SHOW_PORT=47474` show an example address on the server page (screenshots without a real LAN address). Settings live in `%APPDATA%\BMS Companion\` (`pc-app.properties`, `bridge-settings.json`, `app.lock`).
- **Browser version:** served at `http://<pc>:47474/` by the running PC program (`?route=mission` opens a route). Headless check: `msedge --headless=new --window-size=1180,820 --virtual-time-budget=40000 --screenshot=out.png http://127.0.0.1:47474/?route=mission` (headless windows are at least 500 px wide).
- **Developer checks:** `"BMS Companion.exe" --selftest out.txt` (struct sizes, parser output), `--dumpstrings out.txt` (with BMS running), `--eztest <EZBoards copy> out.txt`, `--api /api/info,/api/mission out.txt`, `--maprender <theater id> <folder> [xFt,yFt]` (all map styles at three zooms as PNGs, headless); the full list is the Developer checks row above. Run checks from a copy of the jar with a scratch `APPDATA` pointed at a copy of a BMS folder. From source: `./gradlew :desktop:run --args="--selftest C:/temp/out.txt"` (call gradlew from PowerShell when the path has spaces).
- **Bump the version:** `NAME` in `app/src/main/java/com/bmscompanion/app/AppVersion.kt` (and `versionCode` in `app/build.gradle.kts`). Nothing else: both build files read that file.
- **Release:** `./gradlew assembleRelease` (copy to `dist/BMS-Companion.apk`) and `powershell -ExecutionPolicy Bypass -File pc/publish-desktop.ps1` (MSI and zip into `dist/`). Release files: APK, MSI, zip. Notes from `CHANGELOG.md`.

## Gotchas
- **The install context has to agree in two places.** `perUserInstall` in `desktop/build.gradle.kts` decides what jpackage builds; `ALLUSERS` in `pc/finish-msi.ps1` decides what the installer asks for. A per-user package sets bit 8 of the summary Word Count ("installs without elevation"), and Windows then refuses `ALLUSERS=1` with "You do not have sufficient privileges to complete this installation for all users of the machine" — elevating does not help, and with UAC off it is never seen. BMS Companion is per machine in both: double-clicking raises the consent prompt on its own. `finish-msi.ps1` fails the build if the two disagree.
- **MSI Upgrade attributes: 0x100 is VersionMin**Inclusive, **0x200 is VersionMax**Inclusive. jpackage writes 257 (MigrateFeatures + 0x100) with an empty VersionMin, so VersionMax is exclusive and a same-version build installs *alongside* the old one instead of replacing it. `pc/finish-msi.ps1` sets 0x200 and fails the build if it is missing. Attributes is part of that table's primary key, so the row has to be deleted and re-inserted, not updated.
- **Swing file choosers must stay off the Windows shell.** The app sets the system look and feel, under which `JFileChooser` walks `sun.awt.shell.Win32ShellFolder2` for icons and the "This PC" list; on many machines (OneDrive, mapped or removable drives) that throws or takes the process down, and it lands on the thread Compose draws on. `pickFolder` sets `putClientProperty("FileChooser.useShellFolder", false)`, opens in a folder that is already known, and catches everything. Every folder it picks can also be typed into Settings.
- **Navigation: one navigate per tap, and no transitions between sections.** `popBackStack` + `clearBackStack` in the same handler, or a cross-fade that keeps a popped destination composing, both end in `IllegalStateException: You cannot access the NavBackStackEntry's ViewModels…` from `LocalOwnersProvider` (navigation-compose 2.8.0-alpha10 asks every composed entry for its ViewModel store). `AppRoot.onTab` uses a single `navigate` for Home and the NavHost uses `EnterTransition.None`/`ExitTransition.None`. Reproduce with rapid rail clicks in the browser build; page errors show up in the CDP console.
- **Java 21 collection methods are a trap.** The app compiles against API 35, so Kotlin binds `LinkedHashSet.reversed()`, `List.getFirst()`, `MutableList.removeFirst()` … as members; they do not exist before Android 15 and throw `NoSuchMethodError` (1.3.1 crashed on Android 9). Write `set.toList().asReversed()`, `list[0]`, `removeAt(0)` instead. Lint does not catch it; `tools/check-apk-compat.ps1` scans the built APK.
- `String.format("%d", double)` crashes at runtime. Convert with `.toInt()` first.
- `TheaterMap` reads `onTap`/`onUserGesture` via `rememberUpdatedState`. Don't key `pointerInput` on lambdas: live data recomposes 4×/s and would cancel taps.
- `briefing.txt` uses CRLF, and EZBoards' `xbrief.exe` fails on LF-only files.
- BMS RWR `bearing[]` is true bearing in radians. Subtract ownship yaw for the scope.
- StringData ids are verified with `--dumpstrings out.txt` against a running BMS (the header comments skip entries). NavPoint `z` is feet (not tens of feet). The hsiBits `Flying` flag is not set in 4.38.1, so flying detection also uses `pilotsStatus == 3`.
- TACAN has two sources in shared memory: UFC (DED, usually the home base from the DTC) and AUX COMM. `live.tacan` prefers the A/A or Y-band one; both are sent as `tacanUfc`/`tacanAux`.
- Tacview sends ejected crews as `Ground+Air+Light+Human+Parachutist`; they map to kind `crew` before the `Air` check.
- **The map's Traffic and Hostiles are two switches, not one inside the other.** Traffic is your own side (friendly, neutral, your flight), Hostiles is theirs, and the filter in `MissionMap.kt` picks one or the other by `Contact.hostile`. Nesting them — which is how it shipped up to 1.3.7 — let Traffic silently govern both, so a pilot who turned the enemy off got them back the moment they turned their own flight on. The AWACS page always had it right (`AwacsSettings.friendlies`/`hostiles`); the map is now the same.
- **Hostile contacts from the live feed are off by default, and kept back at the source** (1.3.8, so the app is no cheat). One PC-wide setting, **Show hostile contacts (live)** (`BridgeSettings.ShowHostiles`, off; settings layout 3 sets it off once for everyone), shown on all three Setup pages (`HostilesCard` in `ui/screens/mission/HostilesSetting.kt`) and set from any device by `POST /api/contacts/hostiles?on=` (`MissionLink.setHostiles`); devices read it as `info.tacview.hostiles` (`HostileContacts.on`, `rememberHostilesOn()`; absent from an older PC = off). While off, `/api/contacts` (`Bridge.contactsFor`, after `KnownSams`) carries no hostile contact — aircraft, ships, ground units, air defences (even at a known site: a live one tells whether the site still stands), crews, contacts of no known side — and only the own side's weapon events (`HostileContacts.strip`); the briefing's threats and the PPT rings (drawn from the briefing and the cartridge, not the feed) and the cockpit's own data stay. Each `MissionLink` strips the same again, and the pages say so rather than look empty: the map's and AWACS page's Hostiles chips are not offered (`HostileContacts.OFF_SHORT`), the Map tab leaves the Picture card out, the Dashboard's Picture card and the Picture board say `HostileContacts.OFF`, the AWACS page shows friendlies only with a note, the VR board page offers no Hostile traffic layer. With it on, the per-device Hostiles switches are a second filter. Check `--hostiletest out.txt` (with a scratch APPDATA: the strip, the migration, the route off and on through `Bridge.feedForCheck`, a device against an older PC)
- **Tacview's `Coalition` from BMS is the country, and `Color` is per country too** (Hellas Blue, Albania Cyan, U.S. Green, N.Macedonia Yellow in one recording). Neither says who is allied; only the campaign's team table does. Comparing coalition names drew every allied aircraft of another nation as hostile.
- DTC `target_N` is steerpoint N+1. Action `-1` marks a user target steerpoint.
- Some launch environments set `NoDefaultCurrentDirectoryInExePath`, and the EZBoards runner removes it for the child cmd.
- `Falcon BMS.exe` detection uses a Toolhelp snapshot (works when BMS runs elevated); `ProcessHandle` would not see its name.
- PC version: don't use `LifecycleResumeEffect` for polling in PC overrides. The window provides its own always-RESUMED `LifecycleOwner`/`ViewModelStoreOwner` (`Main.kt → WindowOwner`), shared with the `NavHostController` hoisted outside the window, because full screen recreates the window (`key(fullscreen)` with `undecorated`).
- PC version: full screen is a recreated undecorated window sized to the monitor, not `WindowPlacement.Fullscreen` (Java's exclusive full screen minimizes when BMS takes focus).
- Browser version: Kotlin/Wasm `LinkedHashMap` is final (no `removeEldestEntry`); `java.*` stand-ins live in packages `java.util`/`java.text` under `web/.../shims`. JS interop goes through `@JsFun`; converting large downloads byte by byte is fine for thumbnails and charts, avoid it for huge files.
- **`PageBasedContent` can only be enabled once per page.** A second `EnableExperimentalFeatures` call answers "already enabled" — an error — and the board publishing again (a count that grew, a kind changed on the PC) then lost its pages. `okbPublishPages` keeps the enabling promise on `window.__bmscFeature` and treats "already enabled" as success; `VrBoard` retries a failed publish a few times.
- **A VR board cannot see the app's state.** The board is a browser tab the PC serves, in its own process, so the Taxi page publishes what it is showing to `/api/taxi` (kept in memory by `Bridge`, never on disk) and the board asks for it once a second. Without a published choice the board works it out from where the jet is standing, which is what a pilot wants the moment they spawn.
- **A clamp that writes state during composition flickers.** The kneeboard map holds its pan inside the theater square so the square always covers the page. Writing that clamp back into the state during composition invalidates the composition, which re-clamps; with *Follow* moving the pan four times a second, the map and the bare board alternated down one edge several times a second, and only at some zoom steps. The clamp is applied where the projection is worked out (`proj()` in both `TheaterMap.kt` copies), never written back. A board's minimum zoom is also the cover now, not the fit: zooming out to the whole theater is what put a band of bare board down the side in the first place.
- **The browser bundle can go stale after a source change.** `compileKotlinWasmJs` and `compileProductionExecutableKotlinWasmJs` re-run, but `…Optimize`, `wasmJsProductionExecutableCompileSync`, `wasmJsBrowserProductionWebpack` and `wasmJsBrowserDistribution` can all stay UP-TO-DATE, so the PC program goes on serving the previous bundle (and `:desktop:run` copies that one into its resources). Symptom: an edit that compiles cleanly has no effect in the browser. Force it with `rm -rf web/build/compileSync web/build/dist web/build/kotlin-webpack` before the build. To check, look in **`bmsc.wasm`, not `bmsc.js`**, and for **UTF-16**: Kotlin/Wasm keeps string literals in a wasm data segment, two bytes a character, so an ASCII `grep` of either file finds nothing however fresh the bundle is. `node -e "console.log(require('fs').readFileSync('web/build/dist/wasmJs/productionExecutable/bmsc.wasm').includes(Buffer.from('<something new>','utf16le')))"`.
- Browser version needs WasmGC (Safari 18.2+, Chrome/Edge 119+, Firefox 120+); `index.html` shows a message on older browsers.
- Maps: every style, tile level and landmark layer is drawn in the same unit square of the theater (`MapProjection`), so styles always align. The maps are laid on the projection string of `NewTerrain/Theater.txt` (PROJ tmerc, theater feet = metres × 3.27998; x = north). `HeightMap.raw` is int16 feet. Water is **not** "height ≤ 0": land below sea level (Jordan valley, Arava, Nile delta) has varying heights, while BMS stores each water body as an exactly flat level (Israel: sea -70, Dead Sea -1457, Galilee -771). Use `tools/extractor/src/heightmap.mjs` (`readHeightmap` → `water` mask). Keep `MAX_Z` in `MapBase.kt` and `maps.mjs` equal.
- `data/geo` coordinates must be integers (the app reads them as `List<Int>`; a float fails the whole file).
- Tanker TACAN: BMS assigns 92Y to the first tanker, then 126Y, 125Y… (TO 1F-16CMAM-34-1-1, TACAN). A TACAN in the briefing notes wins. Frequencies follow the callsign in the theater's RadioMap (`data/radio`).
- BMS does not export the text of its AWACS/ATC radio calls: the sim assembles them from `Data/Sounds/CommFile.xml` fragments and draws subtitles itself. Shared memory, the Tacview stream (`0,Event=Message` carries weapon events only) and the log files have nothing, so the mission log derives events instead of transcribing calls.
- **A printed latitude and longitude is not the maps' projection.** BMS's own figure (its ACMI recordings: `T=lon|lat|…|U|V`, U/V = feet ÷ 3.28084; its AIPs' "BMS coord") is Weapon Delivery Planner's grid over three figures of the terrain BMS flies the theater on — size, centre, heightmap length (`projection` in `index.json`, `heightmapBytes`): feet ÷ 3.28084, the centre's forward projection less half the theater, one heightmap sample (31.25 m) north. `Theater.txt`'s projection string lies 140-220 m from it on average (up to 290 m) wherever it was checked; the 1.3.8 test builds printed with the string and called it BMS's own (D26 in `docs/WDP-PORT.md` has the evidence). Everything that prints or reads a latitude and longitude goes through `WdpCoords.coordData` + `PopupCoords` (the Planner's pages, windows, Map page and kneeboard pages, and outside the Planner only the airfield page's Info box, `divertCoords` in `DivertBlock.kt`); the Falklands (2,048 km, no recording or BMS figure; 34 fields lie a median 460 m from the real airports, as BMS's grid does on the others) keep the string. Check a theater with `--acmicoords` on a recording of it, and every theater's fields with `--divertcheck`.
- **Tacview's positions have to be put in the same frame as the jet.** Ownship comes from shared memory and is exact; every other aircraft comes from Tacview, whose flat U/V are offsets from a reference of its own, and the two frames need not agree. Any difference displaces every contact by the same amount — invisible on a theater map, and on a ground chart it parks the other aircraft on the grass. Our own aircraft appears in both frames, so `TacviewClient.snapshot` takes the difference at that one point and subtracts it from every contact (`MAX_FRAME_SHIFT_FT` guards against the nearest aircraft not being ours). It is self-correcting, so it holds at every airfield in every theater.
- **A ramp spot's `s` is not "sheltered".** It is BMS's point type 11, meaning the spot records what size of aircraft fits, which is true of most spots at most fields — reading it as shelter made 302 of Osan's 334 spots "hardened". Whether a spot has a roof comes from the field's own object list: a shelter or a hangar standing over it (`coveredBy` in `airfields.mjs` → `AfSpot.covered`, 17,371 of 118,478 spots across the nineteen theaters). The chart draws those with a roof ridge and a heavier outline, and the clearance wording uses the same flag.
- **The on-screen keyboard never resizes the app** (`ui/components/KeyboardLift.kt`). `WindowInsets.safeDrawing` includes the keyboard: padding the frame by it laid every page out again in the half left, frame by frame as the keyboard slid in, and the Planner's fitted page shrank and stuttered. `AppRoot` pads by `rememberSteadyBars()` (system bars and cut-out, held as they were while the keyboard or an editor bar is up — Android shows its navigation bar with the keyboard even in immersive mode), the rail and the bottom bar get no insets of their own, and `Modifier.keyboardLift()` on the root lifts the whole app by a layer translation just far enough for a focused field the keyboard would cover (it hears the field's bring-into-view request). An editor that sits on the keyboard itself holds the lift off (`KeyboardLift.hold`). Never add `imePadding()` to a page.
- **A WDP page must not recompose whole for one box** (Android, 1,000+ controls on the DataCard). Each control reads the values through `WdpLiveValues` (one counter per control, bumped for the controls whose keys changed and their containers, after the composition: `update` + `flush`), `Palette` and `Inherited` are data classes (identity-compared they made every control recompose every time), `WdpFormView` hands down stable callbacks and content, on a finger's device the page is an Offscreen layer while unzoomed, and a box there is plain text until a mouse press arms it (`TypingState.armed`: a `BasicTextField` per box was three quarters of a page's composition). Profile a release build with simpleperf (`<profileable android:shell="true"/>` temporarily) and deobfuscate with the R8 mapping.
- **A screen that holds the pointer must hand focus back.** The ground chart takes every pointer event for panning, zooming and tapping spots; leaving it left the window's focus owner gone, and the search field on the page behind was dead until the window was minimised and reopened. Two halves: the chart clears focus in `onDispose`, and `SearchInput` grabs focus itself on a **press** (`PointerEventPass.Initial`, `PointerEventType.Press` only — on any event a mouse merely crossing the field would steal the keyboard).
- Never test Media delete on the real BMS folder: point `PicturesDirOverride` at a copy (Falcon BMS settings), and clear it afterwards.
- **Config: nothing in `BmsConfig` may throw, and no settings file is written in place.** Falcon BMS is often installed where Windows will not let an ordinary program write (Program Files, a read-only drive, a file another tool holds open). Every disk step goes through `attempt`, and the reason travels back in `CfgState.error` / `CfgFile.error` for the page to show in red — a button that does nothing and says nothing is the failure this guards against. Writes go through `writeSafely` (temp file beside it, then an atomic move), because `writeText` truncates first and a write that fails half way would leave a pilot with an empty Falcon BMS config. Test with `--cfgtest` against a **copy** of `User/Config`; it refuses a folder holding `Falcon BMS.exe` and refuses to re-run over its own `BackUp`, and a folder with writes denied (`icacls … /deny '*S-1-1-0:(OI)(CI)(W)'`) is the other case worth running.
- **Copying a BMS folder resets file times, and the checks read them.** `cp -r` (and Explorer) gives every file a new created time and can reset modified times; the campaign listing's order, the bulk-copy rule, "changed since" and `--camtest`'s inventory all read them. Copy a fixture with `cp -rp` (or put the times back from the original) before trusting a FAIL about order or dates.
- **Theater definitions are not tidy.** `.tdf` names carry trailing spaces ("Carrier War "), paths differ in case (`Add-on KTO 80s`), and `Strings.txt` may separate the id from the text with a space rather than a tab ("341 RELOCATE"). Trim, match paths without case, split on the first run of whitespace (`Theaters`).
- **The stock TE `.ini` files ship with BMS.** Every `TE_BMS_*.ini` and `TR_BMS_*.ini` in `Data/Campaign` carries the same install time stamps as `Atc.ini` and `Save0-5.cam`: they are BMS's, not the pilot's — and the Planner writes them anyway when that TE is open, as WDP does; only the campaign starts (`CampaignStarts`) are refused. **`Auto Save.ini` can hold another flight**: BMS rewrites `<save>.ini` under whatever save is loaded, so a mission file beside a save proves nothing until its points match the briefed flight (`MissionDtcFile`, `CampFlight.missionIni`). **`Auto Save.twx` is shared the same way**: `Auto Save.cam` and `Auto Save.tac` both write it, so the DataCard asks for a save's weather with `save=` and the PC refuses another save's file in a sentence (`PcFileRoutes.otherSave`: a campaign's `.twx` is written in the same millisecond as its `.cam`, and its last-check field is BMS's last weather check, up to a few minutes before the save's clock, never after it).
- **In 4.38.1 the cartridge's route slots are empty.** `User/Config/<callsign>.ini` holds only precision targets (STPT 15-22 after a Recon); the route is in the mission file beside the save. So "the cartridge's non-zero steerpoints" is the recon bank, not the flight plan — the route line joins only STPT 1-24 with action ≥ 0 (`MergedMission.steerpoints`; tables and markers use `allSteerpoints`, and `preplannedThreats()` leaves out the markers that `preplannedPoints()` keeps).
- **A PPT range is feet, always.** Up to 1.3.7 the bridge took any range up to 500 as nautical miles, so an AWACS or tanker marker (0.1 ft in `Ppt.ini`) became a 0.1 nm threat ring. A range under 100 ft is a marker (`DtcParser.MARKER_FT`). A DTC value that reads as NaN or Infinity (a hand-edited file) is 0: kotlinx refuses to encode non-finite numbers and `/api/mission` failed with it.
- **A save's air-defence site is spotted by the team that controls the flight's team.** In Korea ROK controls the U.S. team, whose own spotted bit is never set: the flight's own bit gave 0 of 178 sites on the Korea test save, the controlling team's 90 (`CampaignBriefing.sites` takes either).
- **A Clear All or a save never loses placed points silently.** `DtcPage.confirmClear` (set by `DtcWiring`) asks before any of the six Clear All buttons wipes a point that has a position, naming them; every save asks once when it would set a point placed in the cartridge as loaded to 0,0,0 (`DtcWiring.zeroed`). One Clear All STPTs followed by a save once zeroed a pilot's Recon targets. The click and outcome checks press every control, Clear All included — which is what DevGuard and their in-memory DTC sources are for.
- **A kneeboard page file's layout depends on who wrote it last**: EZBoards writes DXT1 without mips, html_brief 32-bit BGRA (16 MB), BMS ships DXT5 with 12 levels (KTO), DXT1 with 12 (Balkans) or one (Hellas). Upd Kneeboard never changes a file's format, and refuses DX10/BC7, DXT3, 24-bit and odd sizes rather than guessing.
- **A page captured from a coroutine must be the page the host has composed.** Setting the half to draw from Upd Kneeboard's loop was sometimes never recomposed, so the half before it was captured in its place (a card's left half written as its right). The loop calls `Snapshot.sendApplyNotifications()`, waits for `KneeboardPages.awaitDrawn(layer, kind, n, side)`, and refuses a half that never came rather than writing the wrong one.
- **Skia must be loaded on one thread before a headless check starts others.** skiko marks its native library loaded before it has finished loading it, so a check whose first Skia use is on two threads at once dies with an `UnsatisfiedLinkError` (`_nMakeRasterN32Premul`). Touch Skia first (`Surface.makeRasterN32Premul(1, 1).close()`).
- **A press outside an open Material menu only closes it.** A headless check that picks from a drop-down and then presses a button must let the menu's popup leave first (~75 ms), or the press is eaten.
- **A `LazyColumn` keeps its scroll position by the first visible item's key.** A list whose content changes with a search or a switch must scroll itself to the top (Open mission, Config), and a "scroll to this line" must wait until the list has been laid out with that line (`FlightPicker.scrollKey`).
- **The browser version draws only the glyphs its fonts have.** Compose for Web has no system fonts to fall back on, and its default font lacks arrows, triangles, squares and ticks (◀ ▶ ◂ ▸ ▾ ■ ▲ ▼ ✓ ✕ ☰ ⋮ …). `web/.../Main.kt` preloads `/fonts/SymbolsFallback.ttf` (a 150 KB DejaVu Sans subset, licence beside it) with `FontFamily.Resolver.preload` before `AppRoot` is shown, and Skia takes any glyph the default font lacks from it. Not in it: emoji and ⤢ — use an icon.
- **The theme's text style breaks WDP's small type.** Content a wiring draws itself (`LocalWdpContent`) gets `LocalTextStyle` without the theme's 24 sp line height and 0.5 sp letter spacing, which pushed the Loadout window's store names and buttons out of their rows on phones and tablets.
- **A button's name on screen is quoted by the Guide.** Rename it in `PlannerGuideText.kt` too; `--planneroutcome guide` fails on the old names.
